What happens when you run
kubectl apply -f deployment.yaml ?

Kubernetes is a system of independent controllers that all watch the API server. There is no central brain — no component "tells" another what to do. Each one observes shared state in etcd, compares it to what it wants, and acts. This page traces a single kubectl apply through every component it touches.

The big picture

A Kubernetes cluster has two halves. The control plane stores desired state and runs controllers. Worker nodes run your pods and report back. Communication goes through the API server.

Control plane (1 or 3 or 5 nodes)

kube-apiserver

The ONLY thing that talks to etcd. Auth, authz, admission, the REST API.

etcd

Strongly consistent key-value store. Holds all cluster state.

kube-scheduler

Picks a Node for each unscheduled Pod. Pure decision engine.

kube-controller-manager

Bag of controllers: Deployment, ReplicaSet, Node, Job, EndpointSlice, ServiceAccount, ...

cloud-controller-manager

Cloud-specific glue: external LBs, node lifecycle, route tables. Absent on kind / bare-metal.

Worker node #1

kubelet

Watches API for pods on this node. Talks to runtime via CRI. Reports status.

kube-proxy

Programs iptables/IPVS so Service IPs route to backend Pods.

Container runtime

containerd / CRI-O. Pulls images, runs containers, manages cgroups.

CNI plugin

Calico / Cilium / kindnet. Assigns Pod IPs, sets up veth pairs and routes.

The 12-step flow of kubectl apply -f deployment.yaml

Every step is colour-coded by the component doing the work. Each component acts independently — there's no single orchestrator pulling strings.

1

kubectl prepares the request kubectl

  • Reads ~/.kube/config to find the API server URL + your client cert/token.
  • Parses your YAML, expands defaults, runs client-side validation.
  • Discovers the resource API path (e.g. /apis/apps/v1/namespaces/demo/deployments).
  • Sends an HTTPS POST (new) or PATCH (apply existing).
2

API server: authentication kube-apiserver

"Who are you?" Identifies the caller using one of:

  • x509 client certificate (most local / kubeadm clusters)
  • Bearer token (ServiceAccount, OIDC)
  • Webhook token reviewer

Output: a user.Info with username + groups. No permissions checked yet.

3

API server: authorization (RBAC) kube-apiserver

"Are you allowed?" Walks every RoleBinding and ClusterRoleBinding and asks: does ANY of them grant verb=create on resource=deployments in namespace=demo?

If no: 403 Forbidden. Done. Otherwise → admission.

4

Mutating admission kube-apiserver

The request is rewritten by a chain of mutators (in order):

  • Built-in: ServiceAccount injection, default StorageClass, default toleration.
  • MutatingAdmissionWebhook: Istio sidecar injector, cert-manager, your custom webhooks.
5

Validating admission kube-apiserver

Last chance to reject. Validators can NOT mutate, only say yes/no:

  • Built-in: ResourceQuota, LimitRange, PodSecurity.
  • ValidatingAdmissionWebhook: OPA/Gatekeeper, Kyverno, your policies.

Reject → 400 back to kubectl. Accept → persist.

6

Write to etcd etcd

API server is the ONLY component that talks to etcd directly. The Deployment object is written under a key like /registry/deployments/demo/k8s-demo.

etcd uses Raft to replicate the write to a quorum of etcd members before acknowledging.

7

API server replies; watchers fire kube-apiserver

kubectl gets 201 Created and prints deployment.apps/k8s-demo created.

Crucially, the API server now broadcasts a watch event (ADDED) to every controller that has an open WATCH /apis/apps/v1/deployments stream.

8

Deployment controller wakes up controller-manager

The Deployment controller's reconcile loop fires:

  • Reads the new Deployment.
  • Sees no matching ReplicaSet exists → creates one (POST to API).
  • Names it k8s-demo-<templateHash> (so a new image == new RS).

That POST loops back through steps 2–7 again — auth, admission, etcd write, watch event.

9

ReplicaSet controller creates Pods controller-manager

Different controller, same pattern:

  • Watches ReplicaSets. Sees the new RS wants 3 replicas, has 0.
  • Creates 3 Pod objects via API (status=Pending, spec.nodeName="").
  • Each POST hits etcd, fires another watch event…
10

Scheduler binds Pods to Nodes kube-scheduler

Watches for pods with empty spec.nodeName. For each one:

  • Filter: which nodes can fit this pod? (resources, nodeSelector, taints, affinity, PV zone…)
  • Score: rank survivors (least loaded, image already cached, balanced spread).
  • Bind: POST /pods/<name>/binding {nodeName: worker2} — that's it. No signal, no push.

The scheduler does NOT start the pod. It only writes the assignment.

11

Kubelet on the chosen node runs the pod kubelet

Each kubelet keeps an open watch filtered to its own nodeName. A new pod assigned to it triggers:

  • Pull image via CRI → containerd → registry.
  • Create the pod sandbox (network namespace + pause container).
  • Call CNI plugin → assigns Pod IP, wires veth pair into the node bridge.
  • Mount Volumes, project ConfigMaps/Secrets/SA tokens.
  • Run init containers in order, then start app containers.
  • Run probes, PATCH pod.status back to API server (running, ready, IP, …).
12

Service traffic gets wired kube-proxy

Independently, on every node, kube-proxy is watching Services + EndpointSlices.

  • The new Pod becomes Ready → API server adds it to the matching EndpointSlice.
  • kube-proxy receives the watch event, regenerates iptables (or IPVS) rules.
  • Result: traffic to ClusterIP:port is now load-balanced to that Pod's IP.
  • CoreDNS independently watches Services → publishes A records cluster-wide.

Component reference

What each box actually does. Bookmark this — it answers 80% of "where does X live?" questions.

kubectl

runs on your laptop

The canonical client. Translates YAML/JSON into REST calls against the API server.

  • Reads kubeconfig for endpoint + credentials
  • Server-side apply, dry-run, diff, rollout, exec, port-forward, logs
  • Has plugins (krew) for everything else

kube-apiserver

control plane · stateless · scales horizontally

The single front door to cluster state. Every read and every write goes through it.

  • Authenticates clients (cert / token / OIDC)
  • Authorizes via RBAC (and Node + ABAC + Webhook)
  • Runs admission chain (mutating then validating)
  • Validates schema, persists to etcd, broadcasts watch events

etcd

control plane · 1, 3, or 5 members (Raft)

Strongly-consistent, distributed key-value store. The cluster's source of truth.

  • Every object lives at /registry/<kind>/<ns>/<name>
  • Supports watch streams (the magic behind every controller)
  • Lose etcd → lose the cluster (back it up!)

kube-controller-manager

control plane · ~30 controllers in one binary

Each controller is a tight reconcile loop: observed → desired → act.

  • Deployment → ReplicaSet → Pod
  • Node controller (mark node NotReady, evict pods)
  • Endpoint / EndpointSlice controller (Service ↔ Pod IPs)
  • ServiceAccount + token controller, Job, CronJob, PV binder…

cloud-controller-manager

control plane · cloud-specific

Cloud-specific glue. Absent on kind, bare-metal, or self-hosted.

  • LoadBalancer Service → cloud LB (ELB, GLB)
  • Node lifecycle (provision / deprovision)
  • Route table programming for Pod CIDRs

kube-scheduler

control plane

Pure decision engine for unscheduled Pods. Plug-in framework with Filter and Score phases.

  • Filter plugins: NodeResourcesFit, NodeAffinity, TaintToleration, …
  • Score plugins: NodeResourcesBalancedAllocation, ImageLocality, PodTopologySpread
  • Output: Pod.spec.nodeName set via the API

kubelet

every worker (and control-plane) node

The agent that turns "spec" into running containers on this node.

  • Watches API for pods assigned to this nodeName
  • Calls Container Runtime via CRI gRPC
  • Runs probes, reports pod status, manages volumes (CSI)
  • Eviction when node is under pressure

kube-proxy

every node (typically a DaemonSet)

Programs the kernel so that ClusterIPs route to backend Pods.

  • Watches Services + EndpointSlices
  • Modes: iptables (default), ipvs, nftables
  • Does NOT proxy traffic itself in iptables/ipvs modes — kernel does

Container runtime (CRI)

every node

Pulls images and runs containers. Talks to kubelet over a Unix socket.

  • containerd (most clusters today), CRI-O
  • Below it: runc / crun for OCI runtime
  • Manages cgroups, namespaces, image cache

CNI plugin

every node · DaemonSet

Gives every Pod a routable IP and decides what traffic is allowed.

  • Calico, Cilium, Flannel, Weave, AWS VPC CNI, kindnet
  • Implements NetworkPolicy (kindnet does NOT)
  • Some (Cilium) add eBPF observability and L7 policy

CoreDNS

cluster add-on · Deployment in kube-system

Cluster DNS. Resolves Service / Pod / external names for every pod.

  • svc.namespace.svc.cluster.local → ClusterIP
  • Headless: returns one A-record per Ready Pod
  • Configured via the coredns ConfigMap (Corefile)

Five things to actually remember

If you take nothing else from this page, take these.

#1

Everything goes through the API server

Components never talk to each other directly. They all go API → etcd → API. That's why kubectl get events sees everything — events are just objects too.

#2

Controllers are reconcile loops

"Observed state vs desired state. Act on the diff. Repeat forever." That single pattern explains Deployment, Job, EndpointSlice, Operators, you.

#3

The scheduler only writes the binding

It does NOT start the pod. It just sets spec.nodeName. The kubelet on that node observes the change and does all the work.

#4

Kubelets only watch their own pods

Every kubelet has a watch filtered by spec.nodeName=<me>. Most events are ignored — they're for some other node.

#5

Services aren't real processes

A Service is a row in etcd. The "load balancer" is iptables / IPVS rules generated on every node by kube-proxy. There's no Service binary running anywhere.

#6

etcd is the only stateful component

Lose any other control-plane process — recoverable. Lose etcd — your cluster is gone. Always back it up. Always.

What about the way back? Status, drift, deletion.

The flow above creates a Pod. The reverse flows are equally important.

Status reconciliation (every few seconds)

Kubelet keeps PATCHing pod.status: container restarts, OOMs, probe results, IP changes. The Pod object's spec is desired state (you wrote it); status is observed state (kubelet writes it).

Drift detection & healing

ReplicaSet controller checks: "I want 3 Ready pods, I see 2." It creates a new Pod. Node controller checks: "Node hasn't sent a heartbeat in 40s." It marks the node NotReady and after 5 min evicts pods so they can reschedule.

Deletion (also through the API)

kubectl delete deploy/k8s-demo sets a deletionTimestamp on the object. Garbage Collector controller cascades the delete to the owned ReplicaSet and Pods (ownerReferences). Kubelet sees pod deletion → sends SIGTERM → waits terminationGracePeriodSeconds → SIGKILL → cleans up sandbox + Volume + IPAM.
